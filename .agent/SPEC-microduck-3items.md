# 从 Microduck 借鉴的三项改造

> 版本：v1.0（2026-11-06 19:30）｜整理：小马
> 来源：[pollen-robotics/microduck](https://github.com/pollen-robotics/microduck)（Pollen Robotics / Hugging Face，2026-07 开源，Apache 2.0）
> 用途：提交 GPT 审核并实施，为车轮方案打地基

---

## 零、为什么借鉴它

Microduck 是 25cm 双足机器鸭，RK3566 主控，15 舵机，走路靠强化学习。它真正值钱的不是 RL，而是三条工程纪律——**这三条和双足、和 RL 都无关，轮式小车同样适用**。

不借鉴的部分：强化学习训练（轮式用 PID 就够）、双足 15 舵机（ESP32 带不动）。

---

## 一、OTA 原子升级 + 自动回滚（P0，现在就能做）

### 现状（已查证）

```
grep "mark_app_valid|ota_get_state_partition|PENDING_VERIFY" main/ → 无结果
```

**固件从没调用过 `esp_ota_mark_app_valid_cancel_rollback()`。**

后果：新固件烧进去后一直处于 `ESP_OTA_IMG_PENDING_VERIFY` 状态。这个状态下每次重启都会被 bootloader 记一次「启动失败」，达到阈值后**自动回滚到上一版**——而我们并不知道这件事会发生。

也就是说：现在不是「没有回滚」，是**回滚在不可控地发生**。

### Microduck 的做法

```
写入新目录 → 验签 → 切软链 current → 健康检查 → 不健康自动退回上一版
```

关键在于「健康检查通过才算数」，而不是「装上就算数」。

### 目标

```
新固件启动
  → 初始化完成（WiFi 连上 或 音频服务就绪）
  → 自检通过（比如：显示正常、音频正常、连上服务器）
  → 调用 esp_ota_mark_app_valid_cancel_rollback()
  → 标记为有效，不再回滚
失败
  → 不调用，bootloader 下次自动回退到旧版
```

### 改动点

| 文件 | 改什么 |
| :--- | :--- |
| `main/ota.cc` | `CheckVersion()` 里对 `ESP_OTA_IMG_PENDING_VERIFY` 的处理补全 |
| `main/application.cc` | 启动自检通过后调用 `mark_app_valid` |
| 新增 | 自检项定义（哪些条件算「健康」） |

### 验收

1. 烧入新固件，串口日志出现 `mark_app_valid` 调用记录
2. 人为造一个启动失败（比如故意不连 WiFi），重启 3 次后自动回到旧版本
3. 正常启动不再被计入失败次数

### 风险

- 自检条件定义太严 → 明明能用却被判失败回滚。建议第一版只检「显示和音频初始化成功」，不检网络。

## 二、双核分工：控制核与语音核分离（P1，为车轮铺路）

### 现状（已查证）

```
xTaskCreatePinnedToCore 使用处：
  main/audio/audio_service.cc:127      （音频）
  main/boards/*/...                     （触摸、电源灯，各板级）
```

有绑核，但**没有「控制专属核」的概念**。所有任务混跑，靠 FreeRTOS 优先级调度。

### 问题

车轮方案里，电机控制需要 10ms 硬循环。一旦语音在播报、屏幕在刷新，控制循环可能被抢占几十毫秒——车在动的时候这是事故。

### Microduck 的做法

```
robotd：唯一能碰电机的进程，50Hz 控制环 + 安全层 + 跌倒判定
其他进程（语音、网络、UI）碰不到电机
```

### 目标

```
Core 1：控制任务（独占，10ms 周期）
  ├── 电机 PWM 输出（现在为空，预留）
  ├── 传感器读取（ToF / IMU）
  ├── 安全判定（超时停车、急停）
  └── 心跳（喂狗 + 上报状态）
Core 0：现有的一切（WiFi、音频、显示、对话）
```

**现在没有电机，也要先把框架搭好**：Core 1 跑一个空循环 + 心跳，验证它不被 Core 0 的负载影响。

### 改动点

| 文件 | 改什么 |
| :--- | :--- |
| 新增 `main/control/control_task.cc/.h` | 控制任务：10ms 周期、绑 Core 1、优先级高于音频 |
| `main/application.cc` | 启动时创建控制任务 |
| 新增 | 指令队列（Core 0 → Core 1，FreeRTOS queue） |

### 验收

1. 启动日志显示控制任务绑在 Core 1
2. 连续 10 分钟语音播报 + 屏幕刷新，控制任务周期抖动 < 2ms（打时间戳统计）
3. 控制任务优先级高于音频任务，但不会饿死音频

### 风险

- 双核抢内存带宽（PSRAM 共享），可能出现新的卡顿。要测。
- 控制任务栈开太大 → 挤占音频。建议 4KB 起。

## 三、救命路径：救命的通道不依赖会死的逻辑（P2）

### Microduck 的做法

> configd、updaterd、btd 这三个，是机器人脑死亡之后还能救它的路径。所以这三个不许依赖 robotd。

它的意思是：**能救命的通道，不能依赖那个可能挂掉的东西。**

### 我们的现状

ESP32 没有进程隔离，只有任务。现在的风险：如果对话逻辑卡死（比如 ASR 阻塞、网络死等），OTA 和配网也可能跟着卡。

### 目标

| 通道 | 依赖什么 | 必须保证 |
| :--- | :--- | :--- |
| OTA 检查 | WiFi + HTTP | 即使对话卡死也能跑 |
| 配网 | WiFi + AP 模式 | 即使音频挂了也能进 |
| 急停（未来） | 硬件中断 | 不经过任何软件逻辑 |

### 改动点

| 文件 | 改什么 |
| :--- | :--- |
| `main/application.cc` | OTA 检查独立成任务，不放在对话主循环里 |
| 未来 | 急停走 GPIO 中断 → 直接拉低电机使能（硬件路径） |

### 验收

1. 人为让对话任务死循环（测试专用开关），OTA 检查仍能触发
2. 配网模式在音频初始化失败时仍可进入

### 风险

- 独立任务会增加内存占用。当前 PSRAM 8MB，够。
- 任务多了调度复杂度上升，要画清楚任务表。

## 四、优先级与依赖

| 顺序 | 改造 | 依赖 | 理由 |
| :-: | :--- | :--- | :--- |
| 1 | OTA 回滚 | 无 | 现在就是隐患，且改动小 |
| 2 | 双核框架 | 无 | 车轮方案的地基，空跑也能验 |
| 3 | 救命路径 | 2 | 需要任务表清晰之后再做 |

三项都**不需要买硬件**，做完再谈电机和雷达。

## 五、给实施方的边界

**可以做**
- 改固件代码、加任务、改 OTA 逻辑
- 新增 `main/control/` 目录

**不可以做**
- 不改表情资源（2.5.6 已定稿：24 eaf / 5FPS）
- 不动 `main/application.cc` 的 `kSecurityLicenseAnchor`
- 不改服务端配置
- 不自行触发 CI 编译、不烧录（编译权在小马）

**交付要求**
- 分支 + 自述文档
- 每项给出「改前 / 改后」的日志对比
- 双核那项要给周期抖动实测数据，不能只说"已绑核"
