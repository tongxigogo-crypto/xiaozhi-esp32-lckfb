# 三方审查协议（小马 / Gemini / GPT）

> 目的：不让任何人基于过期的代码给结论。
> 违反第 1 条的审查，一律退回重做。

---

## 一、审查前置（缺一不可）

审查方必须先跑这三条，并把原文贴出来：

```bash
git -C <repo> rev-parse --short HEAD
git -C <repo> status --porcelain | wc -l
git -C <repo> rev-parse --short fork/main
```

| 结果 | 处理 |
| :--- | :--- |
| dirty 数 > 0 | **拒绝审查**。让对方先提交或 stash，把基线固定下来 |
| HEAD ≠ fork/main | 可以审，但必须写明"审的是本地未推送版本 `xxxxxxx`" |
| 读不到仓库 | 直接说读不到，不要用记忆补 |

## 二、审查输出格式（三档 + 一条证据）

```
必须改
1. <问题>｜证据：<文件:行 或 命令输出>｜动作：<具体做什么>

建议改
...

可忽略
... （写清为什么不影响本次目标）
```

**禁止**：只给结论不给证据、把"我认为"写成"实际是"、引用没跑过的日志。

## 三、三类 Agent 的边界

| 角色 | 能改 | 不能改 |
| :--- | :--- | :--- |
| **小马（WorkBuddy）** | Mac 服务端、frp/VPS、编译流水线、固件代码 | 素材源文件、人设文案 |
| **Gemini** | 固件代码、表情资源导出 | 服务端配置、VPS |
| **GPT** | 只审查，不改代码 | 任何文件 |

跨边界要先在 `PROJECT_STATE.md` 的租约表里换手，不许两边同时改同一片。

## 四、什么时候必须交叉审查

| 触发 | 谁审 | 产出 |
| :--- | :--- | :--- |
| 合入 main 前 | 另一方 | 一份二档结论，落 `docs/review/<commit>.md` |
| 出固件产物前 | 另一方 | 确认版本号、SHA256、分区参数 |
| 连续失败两次 | 第三方 | 判断是方案问题还是执行问题 |

单一 Agent 连续迭代超过 3 轮没突破，必须换人看，不许原地重试。

## 五、冲突仲裁

谁的证据硬听谁的，顺序：

1. 实测输出（命令原文、hash、日志）
2. 官方文档 / 原理图
3. 代码本身
4. 推断（必须标"推断"）

**同一条结论，两方各说各的**：把两边命令都跑一遍，以能复现的那次为准。都复现不了，标"未复核"，不许当成事实写进文档。

## 六、可粘贴的审查提示词

```
先跑这三条并贴出原文：
  git rev-parse --short HEAD
  git status --porcelain | wc -l
  git rev-parse --short fork/main

dirty 数不为 0 就直接退出，告诉我"基线未固定，无法审查"。

基线固定后，按"必须改 / 建议改 / 可忽略"三档输出，
每条后面必须跟：证据（文件:行 或 命令输出）+ 具体动作。
没跑过的日志、没读过的文件，不许当成证据。
```
