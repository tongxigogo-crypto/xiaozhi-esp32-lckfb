# 第一部分：服务端（改完重启，不编译）

## S1｜记忆裁剪前先归档（P0）

### 现状

```python
# core/utils/memory_obsidian.py:22
MAX_MACHINE_CHARS = 2200
```

两套清理路径行为不一致：

| 场景 | 代码位置 | 行为 |
| :--- | :--- | :--- |
| 超 90 天自然遗忘 | `memory_obsidian.py:384-390` | ✅ 追加到 `99-归档/forgotten.jsonl` |
| 超上限裁剪 | `memory_obsidian.py:428-462` | ❌ `result.remove(popped)`，**直接丢** |

2026-11-06 20:02 的日志证明它真的发生了：

```
记忆卡机器维护区字数超过上限 (2236/2200)，开始按档位从低到高裁剪...
裁剪完成：极端降级后字数降至 2197/2200
```

被砍掉的「仅印象」整档，现在永久消失了。

### 目标

裁剪掉的条目写入同一个 `forgotten.jsonl`，并标记来源：

```json
{"text": "...", "tier": "模糊", "last": "2026-08-01", "hits": 2,
 "archived_at": "2026-11-06T20:02:20", "reason": "trim"}
```

`reason` 取值：
- `decay` —— 自然遗忘（现有逻辑，需补这个字段）
- `trim` —— 超上限裁剪（新增）

### 改动点

| 位置 | 改什么 |
| :--- | :--- |
| `memory_obsidian.py:428-462` | 三个裁剪分支删除前先归档 |
| `memory_obsidian.py:388-390` | 现有归档补 `reason: "decay"` |
| 新增 | `_archive_items(items, reason)` 复用函数 |

### 验收

1. 临时把 `MAX_MACHINE_CHARS` 改成 500 触发裁剪
2. `forgotten.jsonl` 新增条目，`reason` 为 `trim`
3. 记忆卡里对应条目消失
4. 归档条目中文不乱码

### 风险

`forgotten.jsonl` 必须用追加模式（`"a"`），不能覆盖已有的 10 条。

## S2｜上限 2200 → 3600（P1）

### 为什么不是瓶颈

| 项 | 数值 |
| :--- | :--- |
| 2200 中文字 | 约 1500 token |
| DeepSeek 上下文 | 128K |
| 占比 | **1.2%** |
| 提到 3600 字后 | **1.9%** |

### 目标

```python
MAX_MACHINE_CHARS = 3600
```

### 验收

- 现有 2236 字的记忆卡不再触发裁剪
- 日志不再出现 `字数超过上限` 警告
- 给出改后每轮 prompt 的 token 增量估算

### 风险

**不能单独上。** 只扩容不改淘汰策略，等于把问题往后推几个月——届时记忆更多，一刀切的损失更大。必须与 S3 同批。

## S3｜按价值逐条淘汰（P2）

### 现状

整档一刀切：

```
1. 先砍掉所有「仅印象」
2. 不够再砍掉所有「模糊」
3. 还不够，按 hits 从少到多删「清楚」
```

### 问题

一条被提过 20 次的「模糊」记忆，和一条只提过 1 次的「模糊」记忆同档一起死。

### 目标

```
价值 = 档位权重 × (1 + ln(1 + hits))

权重：清晰 5 / 清楚 4 / 模糊 2 / 仅印象 1
```

从低到高逐条淘汰，直到满足上限。

举例：

| 记忆 | 档位 | hits | 价值 | 现逻辑 | 新逻辑 |
| :--- | :--- | :-: | --: | :--- | :--- |
| A | 模糊 | 20 | 8.1 | 砍 | **留** |
| B | 模糊 | 1 | 3.4 | 砍 | 先砍 |
| C | 清楚 | 1 | 6.8 | 留 | 留 |

A 比「清楚」档的 C 还活得久——被反复提起的事才是真重要。

### 改动点

| 位置 | 改什么 |
| :--- | :--- |
| `memory_obsidian.py:411-465` | 重写裁剪函数 |
| 新增 | `_item_value(item)` |

### 验收

构造 5 条测试记忆（不同档位、不同 hits），触发裁剪，被淘汰顺序须符合价值排序。日志要打印明细：

```
淘汰 [模糊] xxx（hits=1, value=3.4）
```

# 第二部分：固件（需编译 + 烧录）

## F1｜OTA 回滚（P0，风险最高）

### 现状

```
grep "mark_app_valid|ota_get_state_partition" main/ → 无结果
```

**固件从没调用过 `esp_ota_mark_app_valid_cancel_rollback()`。**

后果：新固件一直处于 `ESP_OTA_IMG_PENDING_VERIFY`。这个状态下每次重启都被 bootloader 记一次失败，够了就**自动回滚**——而没人知道它什么时候会退。

不是「没有回滚」，是**回滚在不可控地发生**。

### 参考做法（Microduck）

```
写入新目录 → 验签 → 切软链 → 健康检查 → 不健康自动退回上一版
```

关键在于「健康检查通过才算数」。

### 目标

```
启动 → 初始化 → 自检通过 → mark_app_valid() → 不再回滚
失败 → 不调用 → bootloader 自动回退
```

### 改动点

| 文件 | 改什么 |
| :--- | :--- |
| `main/ota.cc` | 补全 `ESP_OTA_IMG_PENDING_VERIFY` 处理 |
| `main/application.cc` | 自检通过后调用 `mark_app_valid` |
| 新增 | 健康判定条件 |

### 验收

1. 串口日志出现 `mark_app_valid` 调用记录
2. 人为造启动失败（如不连 WiFi），重启 3 次后自动回旧版
3. 正常启动不再被计入失败次数

### 风险

**自检条件定太严 → 明明能用却被判失败回滚。** 第一版只检「显示 + 音频初始化成功」，不检网络。

## F2｜双核分工（P1）

### 现状

```
xTaskCreatePinnedToCore 使用处：
  main/audio/audio_service.cc:127
  main/boards/*/...（触摸、电源灯）
```

有绑核，但**没有「控制专属核」**。

### 问题

车轮方案里电机控制需要 10ms 硬循环。语音播报 + 屏幕刷新时可能被抢占几十毫秒。

### 目标

```
Core 1：控制任务（独占，10ms 周期）
  ├── 电机 PWM（现为空，预留）
  ├── 传感器读取
  ├── 安全判定（超时停车、急停）
  └── 心跳
Core 0：WiFi、音频、显示、对话
```

**没有电机也要先搭框架**：Core 1 跑空循环 + 心跳，验证不被 Core 0 负载影响。

### 改动点

| 文件 | 改什么 |
| :--- | :--- |
| 新增 `main/control/control_task.cc/.h` | 控制任务，绑 Core 1，优先级高于音频 |
| `main/application.cc` | 启动时创建 |
| 新增 | Core 0 → Core 1 指令队列 |

### 验收

1. 日志显示控制任务绑在 Core 1
2. 连续 10 分钟语音 + 屏幕刷新，控制周期抖动 **< 2ms**（打时间戳统计）
3. 控制任务优先，但不饿死音频

### 风险

双核共享 PSRAM 带宽，可能引入新卡顿。控制任务栈建议 4KB 起，别开太大挤占音频。

## F3｜救命路径（P2）

### 参考做法（Microduck）

> configd、updaterd、btd 这三个，是机器人脑死亡之后还能救它的路径。所以这三个不许依赖 robotd。

### 我们的风险

ESP32 没有进程隔离。如果对话逻辑卡死（ASR 阻塞、网络死等），OTA 和配网可能跟着卡。

### 目标

| 通道 | 必须保证 |
| :--- | :--- |
| OTA 检查 | 即使对话卡死也能跑 |
| 配网 | 即使音频挂了也能进 |
| 急停（未来） | 走硬件中断，不经过软件 |

### 改动点

| 文件 | 改什么 |
| :--- | :--- |
| `main/application.cc` | OTA 检查独立成任务，移出对话主循环 |

### 验收

1. 人为让对话任务死循环（测试开关），OTA 检查仍能触发
2. 音频初始化失败时仍可进配网

### 风险

任务变多，调度复杂度上升。要做一张清晰的任务表（名字/核/优先级/栈大小/周期）。
