# 记忆卡改造方案

> 版本：v1.0（2026-11-06 20:18）｜整理：小马
> 对象：`core/utils/memory_obsidian.py`（服务端，改完重启生效，**不涉及固件编译**）
> 用途：提交其他 Agent 审查并实施

---

## 零、为什么要改

今天 20:02 服务端日志：

```
记忆卡机器维护区字数超过上限 (2236/2200)，开始按档位从低到高裁剪...
裁剪完成：极端降级后字数降至 2197/2200
```

**"仅印象"整档被删掉了，而且没有进归档。** 那些记忆现在永久丢失。

查代码发现两套清理路径行为不一致：

| 场景 | 代码位置 | 行为 |
| :--- | :--- | :--- |
| 超 90 天自然遗忘 | `memory_obsidian.py:384-390` | ✅ 追加到 `99-归档/forgotten.jsonl` |
| 超上限裁剪 | `memory_obsidian.py:428-462` | ❌ `result.remove(popped)`，**直接丢** |

同一份数据，两种对待方式。这是首要问题，比"上限太小"严重。

---

## 一、上限从 2200 提到 3600（P1）

### 现状

```python
# memory_obsidian.py:22
MAX_MACHINE_CHARS = 2200
```

### 这个数字为什么不是瓶颈

| 项 | 数值 |
| :--- | :--- |
| 2200 中文字 | 约 1500 token |
| DeepSeek 上下文 | 128K |
| 占比 | **1.2%** |
| 提到 3600 字后占比 | **1.9%** |

### 目标

```python
MAX_MACHINE_CHARS = 3600
```

### 验收

- 现有记忆（2236 字）不再触发裁剪
- 日志不再出现 `字数超过上限` 警告

### 风险

上限调高后，prompt 稍微变长（+700 token）。对延迟影响可忽略，但要注意：**记忆条目越多，LLM 抓重点越难**。所以这一条不能单独做，必须和第三条（按价值淘汰）配合。

---

## 二、裁剪前先归档（P0，最紧急）

### 现状

三个裁剪分支都是直接删：

```python
# 分支 1
result = [it for it in result if it.get("tier") != "仅印象"]
# 分支 2
result = [it for it in result if it.get("tier") != "模糊"]
# 分支 3
result.remove(popped)
```

而自然遗忘那条路径是这样的（`memory_obsidian.py:388-390`）：

```python
# 将已遗忘数据追加至 50-小肥鱼/99-归档/forgotten.jsonl（不删数据）
if forgotten_items:
    ...
```

### 目标

裁剪掉的条目，写入同一个 `forgotten.jsonl`，并标记来源：

```json
{"text": "...", "tier": "模糊", "last": "2026-08-01", "hits": 2,
 "archived_at": "2026-11-06T20:02:20", "reason": "trim"}
```

`reason` 区分两种来源：
- `decay` —— 自然遗忘（现有逻辑，补上这个字段）
- `trim` —— 超上限裁剪（新增）

### 改动点

| 位置 | 改什么 |
| :--- | :--- |
| `memory_obsidian.py:428-462` | 三个分支删除前调用归档函数 |
| `memory_obsidian.py:388-390` | 现有归档逻辑补 `reason: "decay"` 字段 |
| 新增 | `_archive_items(items, reason)` 复用函数 |

### 验收

1. 人为把 `MAX_MACHINE_CHARS` 临时改成 500，触发裁剪
2. `forgotten.jsonl` 新增条目，`reason` 为 `trim`
3. 记忆卡里对应条目消失
4. 归档条目能被人读懂（不是乱码）

### 风险

- 归档文件会持续增长。当前 1.2KB / 10 条，按这个速度一年也就几万条，无所谓。
- 要保证写入是追加（`"a"` 模式），不能覆盖已有 10 条。

## 三、裁剪策略改为按价值逐条淘汰（P2）

### 现状

整档一刀切：

```
1. 先砍掉所有「仅印象」
2. 不够再砍掉所有「模糊」
3. 还不够，按 hits 从少到多删「清楚」
```

### 问题

一条被提过 20 次的「模糊」记忆，比一条只提过 1 次的「模糊」重要得多，但现在同档一起死。

### 目标

按价值排序，从低到高逐条淘汰，直到满足上限：

```
价值 = 档位权重 × (1 + log(1 + hits))

档位权重：清晰 5 / 清楚 4 / 模糊 2 / 仅印象 1
```

举例：

| 记忆 | 档位 | hits | 价值 |
| :--- | :--- | :-: | :-: |
| A | 模糊 | 20 | 2 × (1+ln21) ≈ 8.1 |
| B | 模糊 | 1 | 2 × (1+ln2) ≈ 3.4 |
| C | 清楚 | 1 | 4 × (1+ln2) ≈ 6.8 |

按现在的逻辑，A 和 B 一起被砍（都在「模糊」档）。
按新逻辑，B 先死，A 比 C 还活得久——这是对的，被反复提起的事才是真重要。

### 改动点

| 位置 | 改什么 |
| :--- | :--- |
| `memory_obsidian.py:411-465` | 重写裁剪函数，改为单次按价值排序 + 循环淘汰 |
| 新增 | `_item_value(item)` 计算价值 |

### 验收

1. 构造 5 条测试记忆（不同档位、不同 hits），触发裁剪
2. 被淘汰的顺序符合价值排序
3. 日志打印淘汰明细：「淘汰 [模糊] xxx（hits=1, value=3.4）」

## 四、可选：分层加载（P3，单独成版）

### 想法

```
清晰 + 清楚  → 每轮都进 prompt（约 20-25 条）
模糊 + 仅印象 → 不进 prompt，被问到时用 search_notes 检索
已遗忘       → 归档，不参与
```

### 为什么放最后

它改的是「读取逻辑」，不只是「清理逻辑」。要动 `read_memory_card()` 和 prompt 拼装处，测试面比前三条大得多。

**前三条做完、稳定跑一周之后再考虑。**

## 六、给实施方的边界

**可以做**
- 改 `memory_obsidian.py`
- 新增内部函数
- 补日志

**不可以做**
- 不改记忆卡的 Markdown 结构（机器维护区 + 人工备注区两段式）
- 不动「人工备注（服务端只读，永不覆盖）」那块
- 不改五档定义（清晰/清楚/模糊/仅印象/已遗忘）
- 不覆盖 `forgotten.jsonl` 已有的 10 条
- 不自行重启服务端（重启由小马做，会断设备连接几秒）

**交付要求**
- 每项给出「改前 / 改后」的日志对比
- 第三条要给出淘汰顺序的实测输出，不能只说"已按价值排序"
- 说明对现有记忆卡（2236 字）的实际影响
